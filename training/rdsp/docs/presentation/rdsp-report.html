Technical report · September 2026

rdsp: heterogeneous pipeline parallelism on Ray and DeepSpeed

Package: ray_deepspeed_pipeline v0.0.1Hardware: NVIDIA H100 80GB (SXM) for the Megatron-Core comparison; NVIDIA L4 24GB (PCIe) for vision-language runsModels: Qwen3-0.6B; Qwen3-VL-2B and -8B
Abstract

rdsp is a pipeline-parallel training runtime that places each pipeline stage in its own group of Ray actors and runs an unmodified DeepSpeed engine inside every group. Unlike Megatron-LM and DeepSpeed's PipelineModule, it does not require stages to share a parallel layout: one stage may run data-parallel on two GPUs while its neighbour runs tensor-parallel on four. This report describes the design, the method we used to show that a pipelined model trains identically to an unsplit one, and a controlled comparison with Megatron-Core on Qwen3-0.6B. With weights, data, fused kernels, gradient precision and the physical host held equal, the two systems produce loss curves that agree to within 0.1% per step. rdsp's throughput is 1.02–1.11× that of Megatron-Core when the GPUs are compute-bound and 1.24–1.30× when host-side kernel dispatch dominates. The use case that motivated per-stage layouts, giving the stage that holds the output projection a second GPU, did not improve throughput at this model size. Stages are built by running each model's own forward pass, so the same runtime trains 25 Hugging Face model families without model-specific code, and each stage reads only its own weights from the checkpoint. On Qwen3-VL-2B and -8B with real weights and images, the pipelined loss equals the unsplit model's to within 3×10−8, and Qwen3-VL-8B trains on eight 24 GB L4 GPUs with its vision encoder on a two-GPU data-parallel stage.

1Motivation

Pipeline parallelism cuts a network by depth into consecutive stages and streams microbatches through them. Once the pipeline is full, every stage waits on the slowest one, so throughput is set by the most expensive stage. In decoder language models the stages are not naturally equal. The last stage holds the final norm and the output projection. For Qwen3-0.6B that projection is a 1,024 × 151,936 matrix (156M parameters), which by floating-point count costs about as much as ten of the model's 28 decoder layers.

The established systems address this only by moving layers. Megatron-LM factors the job into a single tensor × pipeline × data grid, and every stage inherits the same tensor- and data-parallel degree (we confirmed this against initialize_model_parallel in Megatron-Core 0.19.2). Its --pipeline-model-parallel-layout option redistributes layers but cannot give one stage more GPUs than another. DeepSpeed's PipelineModule carries the same restriction.

rdsp was built to remove that restriction without forking either framework. Each stage declares its own GPU count and its own mix of data, tensor, sequence and expert parallelism. The stage runs a stock deepspeed.initialize() engine, and Ray places and supervises the stage's processes. A secondary goal was well-defined failure behaviour: a failed step must either leave the model untouched or lock the pipeline until it is restored, never leave stages silently out of step with each other.

The current target is a vision-language model of about 30B parameters on GPUs without NVLink, such as L4 and L40S. Two properties of these models make per-stage layouts attractive. The vision encoder has few parameters but processes several times more tokens than the language model sees per row, so the stage that holds it is compute-heavy and splits well across data-parallel GPUs. And tensor parallelism, the usual way to split a layer, depends on fast GPU-to-GPU links, while pipeline stages exchange only one activation tensor per microbatch.

2System design

2.1Planning

A call to rdsp.initialize() lowers the user's PipelineConfig into a frozen ExecutionPlan before any process is started. Lowering locates the model's block list (the longest ModuleList of identical modules) and cuts it in one of three ways: into equal layer counts, at explicit indices, or into stages of equal estimated cost (BalancedTransformerBlocks). Everything before the block list (embedding, vision encoder) goes to the first stage; the final norm and output projection go to the last. It then derives each stage's rank grid (GPUs = data × sequence × tensor degree) and writes each stage an ordinary DeepSpeed configuration with its own per-rank micro-batch size and parallel settings. Two settings are overridden on purpose:

  • gradient_accumulation_steps is forced to 1, and the adapter scales the loss by 1/M for M microbatches. If DeepSpeed counted micro-steps itself, it would run the optimizer as soon as a stage finished its own backwards, before the other stages had finished theirs.
  • gradient_clipping is forced to 0. DeepSpeed defaults to 1.0 and would clip each stage by its own gradient norm, which is not the global-norm clipping a single-model run performs. Explicit clipping is rejected until global-norm clipping is implemented.

The cost-balanced cut estimates a block's cost by its parameter count, since compute per token is proportional to it. Embeddings count as zero because they are lookups. The first stage also carries the vision encoder, whose estimate is its parameter count times vision_token_ratio, the number of tokens it processes per text token (image patches per row divided by sequence length; about 3 for one 448-pixel image in 256 tokens). The last stage carries the norm and output projection. A stage's cost is divided by its GPU count, since data, tensor or sequence parallelism splits its work. The cut minimises the most expensive stage; among cuts that achieve that minimum it takes the one with the smallest sum of squared stage costs, so no stage is left nearly idle. Cuts never separate the vision encoder from the first blocks it feeds directly (Qwen3-VL adds vision features inside blocks 0–2 of the 8B model). For Qwen3-0.6B on four stages this gives 9·9·9·1 blocks; for Qwen3-VL-32B on eight, 7·9·9·8·8·8·8·7.

Shared parameters that would land on two stages, such as tied input and output embeddings, are rejected rather than silently duplicated. The plan is hashed, and checkpoints record the hash.

2.2Building a stage from any Hugging Face model

A stage must run a contiguous slice of the model, but a Hugging Face model is not a list of layers: it is a forward() function that prepares inputs (masks, position ids, rotary tables, image features) and then loops over its blocks. rdsp does not rewrite that function per architecture. Each stage holds a copy of the model's whole module tree and runs the model's own forward pass (Figure 2):

  • Blocks owned by other stages are replaced by pass-throughs that return their input in the same form the real block would (a tensor, or a tuple for models such as Bloom).
  • Other modules whose parameters the stage does not own (the vision encoder and embedding on later stages, the norm and head on earlier ones) are replaced by stand-ins. A stand-in returns its input, or zeros for an embedding, and keeps a zero-byte placeholder of its weights for model code that reads their data type.
  • A hook before the stage's first block replaces the block's input with the hidden state received from the previous stage, and its keyword arguments with those received alongside it.
  • A hook before the first block after the stage's range takes that block's input as the stage output. This includes any work the model does between blocks (Qwen3-VL adds vision features after its first blocks) and excludes work after the last block (norm, head, logit soft-capping), which belongs to the last stage.

The arguments a block receives, such as rotary tables, attention masks, position ids or ALiBi biases, are part of what crosses a boundary, because later stages cannot always recompute them: Qwen3-VL's positions depend on where the images sit in the sequence, which only stage 0 sees. The first stage's loop still calls every later block (as a pass-through), so it records each block's arguments, and blocks that receive the same tensors share one entry. This handles models whose block types take different arguments, such as Gemma3's local and global attention layers. Blocks that return a tuple send its length once per step, so the next stage's pass-throughs return the right form before any of its own blocks has run. The cost is extra traffic of about 2 × head dimension values per token on top of the hidden state: about 5% for Qwen3-VL-32B (head dimension 128, hidden size 5,120). The hooks cost about 0.1 ms of CPU time per stage and microbatch.

This builder is used for every Hugging Face model except Llama, Qwen3 and Qwen3-MoE running SDPA or flash attention. Those keep a hand-written stage (CausalLMStage) that recomputes positions locally instead of sending them. Non-Hugging Face models built as a plain sequence of blocks use a generic chain.

2.3Placement and start-up

For each stage, rdsp reserves a Ray placement group with the STRICT_PACK strategy, so all of a stage's GPUs sit on one host and its intra-stage collectives stay on NVLink. It starts one actor per GPU. The driver holds the model only as an empty skeleton on PyTorch's meta device (no memory for weights); each actor reads its stage's tensors from the checkpoint's safetensors files, so no process ever holds the whole model. When a checkpoint stores only one of a tied pair (Qwen3-VL-2B ties its embedding and output projection), the untied copy is read from the tensor the model's tied-weights map names. The actors of a stage then form their own torch.distributed world, and each calls deepspeed.initialize() on the stage module. After start-up, every rank reports the coordinates DeepSpeed assigned it; the driver checks them against the plan's grid and refuses to proceed on a mismatch.

Last, every rank of every stage joins two additional NCCL process groups that span the whole pipeline: one carries activations downstream, the other carries input gradients upstream. These are standalone ProcessGroupNCCL objects built from a TCPStore hosted in the first rank of stage 0; DeepSpeed's default process group is left untouched. Two groups are needed because NCCL completes operations on a communicator in issue order. With one shared group, a rank waiting for a gradient could be queued behind its own outgoing activation, and its neighbour in the same situation would deadlock with it. Every link is exercised once with a one-element tensor during start-up, so no connection is established inside a timed step.

2.4Executing one step

engine.train_batch() first takes exactly M microbatches from the data iterator; a short iterator fails the step before any work is dispatched. The driver then increments a generation counter and computes each stage's one-forward-one-backward (1F1B) op list. It sends each rank a single Ray call carrying that list. Stage 0 also receives its inputs and the last stage the labels. For a vision-language model the inputs are a dictionary: row-shaped values (token ids, masks) are split across a stage's data-parallel ranks by row, and values that are not row-shaped (the packed image patches and their grid sizes) are given per row and concatenated for each rank's rows.

From then on the stages run without the driver. A rank receives its input over the forward group, detaches it and marks it as requiring a gradient (this is where one stage's autograd graph ends and the next begins), runs the forward pass through its DeepSpeed engine, caches input and output, and posts an asynchronous send downstream. For a backward, the rank receives the output gradient g and propagates it with

engine.backward((output * g).sum())

a vector-Jacobian product whose gradient with respect to the output is exactly g. This keeps every backward inside DeepSpeed's public API, which matters because DeepSpeed's ZeRO-0 hooks reject a direct tensor.backward(g). Only the step's final backward is flagged as a gradient-accumulation boundary. That is where DeepSpeed reduces gradients across the stage's data-parallel ranks.

When a rank has run all its backwards and holds no cached activations, it reports ready. The driver collects every rank's reply. Only when all stages are ready does it send an apply command, which calls engine.step() exactly once per rank. An 8-stage pipeline therefore costs 16 Ray calls per step.

2.5Connecting stages with different layouts

Each rank owns a cell of a microbatch: a contiguous block of rows (split across data-parallel ranks) and of sequence positions (split across sequence-parallel ranks). Tensor-parallel ranks share a cell. DeepSpeed's AutoTP finishes every row-parallel layer with an all-reduce, so they hold identical boundary activations. The routing rule follows directly from this:

  • A receiving rank takes one message from every sending cell that overlaps its own and assembles the region it needs. The full microbatch is never gathered on one rank unless that rank's cell is the whole microbatch.
  • Only the tensor-parallel rank 0 of each sending cell transmits; every tensor-parallel peer of the receiving cell gets its own copy.
  • The block arguments that travel with the hidden state are routed the same way, which requires them to be laid out rows first. Only the hidden state carries a gradient back.
  • Gradients take the same routes in reverse and are rescaled on arrival. DeepSpeed averages gradients over a stage's data-parallel ranks and sums them over sequence shards, so the gradient entering stage s must equal dps · ∂L/∂(output of s). A gradient crossing from stage s+1 is therefore multiplied by dps / dps+1.

The layout constraints come from DeepSpeed, not from rdsp. Sequence parallelism is not allowed on the last stage, because the shifted-label loss straddles sequence shards. AutoTP and Ulysses sequence parallelism cannot share a stage, because AutoTP replaces the sequence-parallel process-group object. Microbatch rows must divide evenly among every stage's data-parallel ranks.

Several further DeepSpeed interactions are handled in the adapter:

  • Under tensor parallelism, Qwen3's per-head q_norm/k_norm weights are replicated, but each rank computes gradients only for its own heads. A hook sums those gradients across the tensor-parallel group so the replicas stay identical.
  • With expert parallelism folded onto tensor parallelism, each rank produces a different partial input gradient; it is averaged at the input of each folded expert layer before being sent upstream.
  • ZeRO-2 keeps a running sum of reduced gradients, and with optimizer offload the sum lives in host memory next to a micro-step counter. Both are cleared when a step is abandoned, so a retry does not add onto the failed attempt.
  • With tensor parallelism, DeepSpeed checks on the first forward that every TP rank received identical inputs, comparing only top-level tensors. Boundary tensors therefore reach the engine as flat keyword arguments.
  • Stages built from Hugging Face models carry the model's tensor-parallel plan and text configuration, which AutoTP, Ulysses and AutoEP read. Most model configurations (about 80% in transformers 5.17, including Qwen3-VL) ship no plan; for those the stage uses the standard split of q/k/v/o_proj and gate/up/down_proj when every block has them.

2.6Memory: recomputation and optimizer offload

Two per-stage settings trade speed for memory. With recompute, each of the stage's blocks keeps only its input for backward and reruns its forward there. This covers the stage's slice of the pipeline's block list and any other block list it owns whole, such as the vision encoder's, which holds most of the first stage's activations for high-resolution images. The block's forward is wrapped, not the block, so parameter names and rdsp's hooks are unchanged. With offload_optimizer, the stage keeps its optimizer state in host memory and steps it on the CPU (DeepSpeed ZeRO-Offload, ZeRO stage 1 or 2).

The budget per parameter decides which to use. In bf16 without offload, DeepSpeed holds about 18 bytes per parameter on the GPU: weights, an fp32 master copy, fp32 gradients and two Adam moments. With offload the GPU holds weights and gradients, and host memory holds about 16 bytes per parameter. A data-parallel stage should use ZeRO-1: ZeRO-2 reduces gradients after every microbatch's backward and, with offload, also moves the running sum through host memory each time, while ZeRO-1 reduces once per step.

2.7Failures and checkpoints

The ready barrier splits failures into two classes. A failure before any rank applies (an exception, a dead actor, or a stuck link hitting the 300 s point-to-point timeout) raises StepFailed and leaves every weight unchanged. The driver resolves every stage's result, so no stage is left mid-step, and rebuilds the point-to-point groups under a new name. At the start of the next generation, each rank discards cached activations and partially accumulated gradients and restores the random-number state it had when the failed generation began, so a retry reproduces a first attempt exactly. A failure after the first apply has been sent may leave some stages updated and others not. The pipeline is then marked poisoned, and every call is refused until load_checkpoint() restores it.

Each stage saves its own DeepSpeed checkpoint and a random-number file per rank; its first rank then records a SHA-256 digest of every file. The driver writes a manifest (plan hash, global step, data position, digests) last, with an atomic rename. A directory without a manifest is an interrupted save and is never loaded. Loading verifies the manifest before touching any rank, rebuilds every actor if any has died (preferring the old hosts, so node-local shards stay reachable), has each stage re-verify its own files, and only then runs DeepSpeed's load on every rank.

3Correctness

Each supported layout was compared against the same model trained unsplit on one device, with identical initialisation, data and optimizer. Three design choices keep the comparison sensitive:

  • The tests use fp32 models and SGD with momentum, not Adam. Adam's per-parameter normalisation hides a uniformly mis-scaled gradient; an Adam-based version of the test passed a deliberately broken build.
  • The training data is learnable, and each test first checks that every step moves the loss by at least 20× the tolerance, so a comparison cannot pass trivially.
  • Beyond the loss trajectory, the tests compare every parameter's update individually.

4Performance evaluation

4.1Method

We compared rdsp against Megatron-Core 0.19.2 on Qwen3-0.6B, starting from the pretrained checkpoint with the embedding and output projection untied, and training on WikiText-103. Megatron-Core runs its own 1F1B schedule (get_forward_backward_func) in a minimal training loop. The Hugging Face weights were mapped into Megatron's layout by hand: query, key and value interleaved per attention group into the fused QKV matrix, gate and up projections stacked, norms placed in Transformer Engine's fused layer-norm slots. The loop asserts that every Megatron parameter receives exactly one weight and that every layer is owned by exactly one rank. Table 3 lists what was held equal.

4.4Where the difference comes from

rdsp's advantage is already present on one GPU, where there is no pipeline at all, so it cannot be a property of the pipeline design. To locate it, we profiled both systems on one H100 with torch.profiler over the same ten steps (Figure 6).

With small microbatches both systems leave the GPU idle for 57–60% of each step while the host issues 25,000–35,000 kernels. About three quarters of rdsp's 181 ms advantage is lower host overhead per kernel; the remainder is the cross-entropy over the 151,936-entry vocabulary, which costs about 82 ms per step in Megatron-Core's default implementation and 17 ms in Liger's. With larger microbatches the GPU is busy for most of the step. There, with the Transformer Engine cross-entropy, Megatron-Core actually spends slightly less time in kernels than rdsp (322 against 342 ms). rdsp stays ahead only because the GPU waits less between kernels. Our reading is that the pipeline mechanism itself adds no measurable cost relative to Megatron-Core's at up to eight stages, and that the remaining difference reflects the two model implementations (Hugging Face with Liger against Megatron with Transformer Engine) rather than the pipeline runtimes.

The heterogeneous layout is slower than a plain fifth stage: 0.93× with the split in Table 5. With the split that equalises estimated per-stage cost, 7 · 7 · 7 · (7+head)×2, it measured 0.91× with 16 microbatches and 0.97× with 4, each against five equal stages on the same host.

The step times show why. With two GPUs, the last stage became the bottleneck at 26–28 ms per microbatch slot against about 23 ms for the other stages, so data parallelism within that stage delivered only about a 1.5× speed-up rather than 2×. Halving a microbatch leaves each GPU too little work to run efficiently, and the stage adds a gradient all-reduce and the split-and-reassemble traffic at both of its boundaries. The output projection also turned out to be lighter in time than in arithmetic, roughly five to six layers rather than ten, because it is a single large, efficient matrix multiplication. At 0.6B parameters, adding a stage is the better use of a GPU. We expect heterogeneous layouts to pay off when one stage's work is large enough to split efficiently and cannot be redistributed by moving layers. Examples are much larger models, very large vocabularies relative to hidden size, vision encoders in multimodal models, and stages that exceed a single GPU's memory.

Three observations. First, the vision encoder dominates the first stage. With the encoder and three blocks on one GPU, that stage spent about 5.3 s per step in forward and backward, against about 1.8 s for stages holding five or six language blocks. By parameter count the encoder is worth about three blocks; in time it is worth about twelve, because it processes three times as many tokens as the language model per row. This is what vision_token_ratio accounts for. Second, recomputing the first stage, the encoder included, cut its peak memory from 22.2 to 9.8 GB for 8% of throughput. Third, splitting the vision stage across two GPUs with ZeRO-1 halves its compute, and the two-GPU layout runs at 660 against 640 tokens/s for eight single-GPU stages: parity, not the gain the stage's compute share suggests. The profile shows why. Under offload every stage spends 2.6–5.3 s per step in the optimizer step on the CPU, about 40% of the step, and that part does not shrink with a better layout. The same layout with ZeRO-2 on the vision stage ran at 240 tokens/s: ZeRO-2 reduced gradients across the two GPUs over PCIe and moved them through host memory after each of the 8 microbatches, raising that stage's backward from 4.2 to 25.5 s.

Qwen3-VL-8B did not fit a four-GPU instance with 192 GB of host memory: offload needs about 16 bytes per parameter on the host, about 140 GB for 8.8B parameters, plus buffers for four worker processes. Qwen3-VL-32B needs eight L40S GPUs (48 GB) and has not been run.

5Threats to validity

  • No repeated measurements. Each cell was run once. The median over 50–140 steps is stable within a run (10th–90th percentile spread of 2–6% in most cells), but run-to-run and host-to-host variance was not characterised beyond the 25% cross-host difference noted in Section 4.1. Ratios below about 1.05, including the 8-GPU compute-bound result, should be read as parity.
  • One host. All results use at most eight GPUs in one host. The Megatron-Core comparison uses Qwen3-0.6B only; the vision-language results use Qwen3-VL-2B and -8B on L4 GPUs with synthetic images and a few training steps per layout. Neither has been tested across hosts or at 32B.
  • Different model code. The comparison is between two stacks, not two pipeline runtimes in isolation: Hugging Face modules with Liger kernels against Megatron modules with Transformer Engine. Section 4.4 attributes most of the observed difference to this.
  • Timing boundaries differ. rdsp is timed at the driver, including Ray round trips; Megatron-Core is timed inside the training process. This biases against rdsp.
  • Model coverage. Families are tested on small random-weight configurations; only Qwen3, Qwen3-VL-2B and Qwen3-VL-8B have run with real weights. The builder needs a forward pass that loops over one list of blocks, so encoder-decoder models are not covered. Block arguments must be laid out rows first to cross a data-parallel boundary, and sequence-parallel boundaries additionally need the sequence in the second dimension. The block-list heuristic takes the longest list of identical modules, which for a vision-language model with a deeper encoder than decoder would pick the encoder. Megatron-Core avoids the coverage question differently: it supports a fixed set of architectures that are re-implemented in its own model code.
  • Cost estimates. Balanced cuts use parameter counts. The output projection took about 5–6 blocks of time against a 10-block estimate on Qwen3-0.6B, and the vision encoder's estimate depends on the image resolution through vision_token_ratio. Cuts can be set explicitly where measurement disagrees.
  • Megatron configuration. Megatron-Core ran with its standard fusions, and with both fused cross-entropy implementations where it mattered. It was not tuned further (for example with CUDA graphs, which would reduce its host overhead in the small-microbatch regime).

6Conclusions and next steps

rdsp demonstrates that pipeline stages with independent parallel layouts can be built from unmodified DeepSpeed engines and Ray actors, with training numerically equivalent to an unsplit model across data, tensor, sequence and expert parallelism. The runtime's orchestration cost is not visible in throughput. Against Megatron-Core under matched conditions it is at parity or somewhat faster, and the remaining difference traces to the model implementations rather than the pipelines. The layout flexibility that motivated the project did not produce a throughput gain at 0.6B parameters. Data parallelism within a single stage does not scale well at this size, and an extra equal stage rebalances the pipeline just as well.

Building stages from each model's own forward pass removes the per-architecture code that pipeline systems usually need: 25 model families, including a vision-language model and one that passes extra tensors between blocks, train identically to the unsplit model. Each stage loads its own weights, so the driver never holds the model. On Qwen3-VL-8B with eight L4 GPUs, a two-GPU vision stage runs at parity with eight single-GPU stages. The limit there is not the pipeline but the optimizer step on the CPU, which offload requires on 24 GB GPUs.

The work that would most change these conclusions, in order of expected information per GPU-hour:

  1. Train Qwen3-VL-32B on eight L40S GPUs (48 GB, 1.5 TB host memory), with and without a data-parallel vision stage, at higher image resolution where the encoder's share grows.
  2. Reduce the optimizer step's share under offload, for example by overlapping the CPU step with the next step's forward, or use GPUs large enough to keep optimizer state on the device.
  3. Repeat each same-host cell two or three times to put error bars on the throughput ratios.
  4. Run the four-host, 32-GPU topology from the design document, which requires a higher GPU allowance or a dedicated cluster, and measure the cross-host point-to-point path.
  5. Implement global-norm gradient clipping across stages, currently the main functional gap for production training.
