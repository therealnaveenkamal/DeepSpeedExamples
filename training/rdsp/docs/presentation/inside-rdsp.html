Inside rdsp: who does what, and where every tensor goes

Everything below is read from the code in src/ray_deepspeed_pipeline/, the design that is running today (stage-local dispatch). Five parties are involved, and the colours stay the same all the way down the page.

The cast

Four pieces of software, one job each

The driver (your process)

  • Plans the split and the schedule
  • Pulls the data, hands it out
  • Starts each step, then waits
  • Decides when every stage may update its weights

Never holds weights or activations: only small results (losses, ok/failed).

api.py · engine.py · compiler.py · schedule.py · coordinator.py

Ray

  • Finds free GPUs; keeps each stage's GPUs on one machine
  • Starts one worker process per GPU
  • Delivers the driver's calls and their small replies
  • Kills and restarts workers on recovery

Does not move activations or gradients between stages.

used in stage_group.py (placement groups, actors, ray.get)

DeepSpeed (one engine per GPU)

  • Runs the stage's layers forward and backward
  • Splits work across the stage's own GPUs (data, tensor, sequence, expert parallel)
  • Averages gradients across those GPUs
  • Runs the optimizer; saves and loads its own checkpoint

Knows nothing about other stages. It is used unmodified.

deepspeed_adapter.py wraps deepspeed.initialize()

rdsp's stage code (in every worker)

  • Runs its stage's op list in 1F1B order
  • Opens GPU-to-GPU lines to every other stage (NCCL)
  • Works out which GPU needs which rows, sends and stitches them
  • Cleans up after failed steps

The layer that makes differently-shaped stages fit together.

stage_worker.py · stage_group.py · p2p.py · boundary.py

The wiring

Three kinds of connection, and what travels on each

The example used everywhere on this page: a 3-stage pipeline where stage 1 has two GPUs sharing its microbatches (data parallel). Each microbatch has 4 rows (4 sequences of text).

Why two rdsp lines instead of one: NCCL delivers messages on one line strictly in order. If activations and gradients shared a line, a GPU waiting for a gradient could be stuck behind its own outgoing activation, and so could its neighbour: a deadlock. One direction per line rules that out.

Phase 1 · once, at start-up

What rdsp.initialize() does, in order

  1. 1

    Check the inputs

    driver
    • No optimizer or scheduler objects: those are built inside each stage from the DeepSpeed config.
    • The DeepSpeed config must stay ordinary: no pipeline, Ray or placement keys in it.
    • The loss function must be serializable: it is shipped to the last stage only.

    api.py · initialize(), _validate_config(), _validate_loss_fn()

  2. 2

    Make the plan

    driver
    • Microbatches per step = DeepSpeed's gradient_accumulation_steps (or PipelineConfig.microbatches; they must agree).
    • Find the layer stack (the longest list of identical blocks) and cut it: equal layer counts, or your explicit cuts. Embedding goes to stage 0; final norm and head to the last stage. Weights shared across stages are rejected.
    • For each stage: its GPU grid (GPUs = data × sequence × tensor parallel) and its own DeepSpeed config: rows per GPU, clipping forced off, and the tensor/sequence/expert settings.
    • Everything goes into a frozen ExecutionPlan with a hash (checkpoints record it).

    compiler.py · lower() → partition.py · partition_parameters() → plan.py · ExecutionPlan

  3. 3

    Reserve GPUs and start one worker per GPU

    driverRay
    • Requires a running Ray (ray.init()); rdsp never starts one.
    • Per stage: build the stage's module (deep copies of its layers), then a placement group that puts all of the stage's GPUs on one machine (STRICT_PACK).
    • Upload the module once (ray.put), then start one StageWorkerActor per GPU. Ray gives each worker exactly one GPU.

    stage_group.py · create_stage_clients()

    Which stage type: rdsp inspects the model (partition.select_stage_builder). Hugging Face Llama-style causal LMs such as Qwen3 get CausalLMStage, which recomputes the rotary position embeddings on every stage; plain sequential models get the generic chain. A model with rotary embeddings but not the rest of that layout is rejected with a clear error. Fixed 2026-09-25: before this, initialize() always used the generic chain.

  4. 4

    Each stage forms its own world, and DeepSpeed starts

    RayDeepSpeedrdsp worker
    • The stage's first worker reports an address (its machine's IP and a free port). Every worker of that stage joins torch.distributed there: the stage world, containing only this stage's GPUs.
    • Each worker calls deepspeed.initialize() on its stage module, with gradient_accumulation_steps = 1. rdsp counts microbatches itself, so the optimizer can only run when the driver says so.
    • Extras by stage type: tensor-parallel rules from the Hugging Face plan, the Ulysses sequence-parallel setup, expert-parallel settings, and two gradient fixes (Qwen3's head norms; folded experts).
    • Each worker reports where DeepSpeed placed it; the driver checks that against the plan (check_mesh).

    StageWorkerActor.bootstrap() → deepspeed_adapter.py · DeepSpeedStageAdapter / _deepspeed_engine_factory()

  5. 5

    Open the forward and backward lines between stages

    driverrdsp worker
    • The driver asks stage 0's first worker for an address, which hosts the address book (TCPStore). The driver passes that address to every worker.
    • Every GPU gets a pipeline-wide number (stage offset + its rank) and joins two NCCL groups spanning all GPUs: fwd and bwd.
    • Each GPU sends a one-number test message to every neighbour it will ever talk to, so no connection is opened in the middle of a step.

    stage_group.py · connect_p2p() → stage_worker.py · StageWorkerActor.init_p2p() → p2p.py · PipelineP2P, _warm_up_links()

  6. 6

    Hand back the engine

    driver
    • A PipelineCoordinator wraps the stage clients; you get a RayPipelineEngine. Its only training call is train_batch(). Calling forward, backward or step on it raises a clear error.

    api.py · _default_coordinator_factory() → engine.py · RayPipelineEngine

Two things to notice while stepping. First, the driver is idle for the whole middle of the step: Ray carried one call to each GPU at the start, and carries nothing again until the replies. Second, stage 1's two GPUs never talk to each other until the last backward. That is when DeepSpeed averages their gradients.

The part Megatron can't do

How rows are routed between differently shaped stages

Pick a shape for two neighbouring stages. rdsp's rule (boundary.py): each GPU owns a block of rows. A receiving GPU takes messages from every sending GPU whose rows overlap its own, and stitches the part it needs. GPUs in a tensor-parallel pair hold identical results, so only one of them sends. The example microbatch has 8 rows.

    When something breaks

    Three outcomes, decided by when it breaks

    Normal

    Every stage ready → update → next step

    1. All GPUs report ready.
    2. Driver sends "apply"; each runs engine.step() once.
    3. global_steps goes up by one.
    Fails before the update

    The step fails cleanly; retry is exact

    1. Any GPU error or a stuck line (timeout, default 300 s) fails the step; no weight has changed.
    2. The driver collects every stage's result so none is left mid-step, then rebuilds the forward/backward lines under a fresh name (epoch + 1).
    3. On the next attempt each GPU throws away leftover activations and half-summed gradients and rewinds its random numbers (begin_generation), so the retry matches a first attempt exactly.
    4. You get a StepFailed error and can simply call train_batch() again.
    Fails during the update

    Pipeline locked until you restore

    1. Some stages may have updated their weights and others not, so the model is inconsistent.
    2. The pipeline is marked poisoned: every train, eval or save call is refused.
    3. load_checkpoint() restores the whole pipeline. If a worker died, all workers are rebuilt, on their old machines where possible, so local checkpoint files stay reachable.

    Saving and restoring

    A checkpoint is one consistent moment across every GPU

    save_checkpoint()
    1. Refused if poisoned; tags can never be overwritten.
    2. Every GPU: DeepSpeed saves its own files (weights, optimizer, scheduler) into <tag>/stage<s>/, plus a random-number file.
    3. Each stage waits for all its GPUs; its first GPU fingerprints every file (SHA-256).
    4. The driver writes manifest.json last: plan hash, step, data position, all fingerprints. Then it moves latest. A folder without a manifest is an unfinished save and is never loaded.

    coordinator.save_checkpoint() · StageWorkerActor._save() · checkpoint.py

    load_checkpoint()
    1. The manifest is checked before anything is touched: same plan, every stage and GPU present, files match their fingerprints.
    2. Any worker dead? Rebuild every stage from scratch (fresh workers, worlds, engines and lines).
    3. Phase 1: each stage re-checks its own files on its own machine. One failure and nothing loads anywhere.
    4. Phase 2: every GPU runs DeepSpeed's load plus its random-number state. Only then is the lock cleared and the step count restored.

    coordinator.load_checkpoint() · _load_phase() · StageWorkerActor._verify() / _load()
