Design & architecture report · September 2026

rdsp: training one model across many GPUs, with Ray between the pieces

A from-scratch explanation of what rdsp is, how every part works, how it compares with NVIDIA Megatron, and what the measurements say. No prior knowledge of distributed training assumed. Dotted-underlined words show a definition when you hover or tap them.

Read this first: the whole project in seven sentences

  1. A neural network is a tall stack of layers; rdsp cuts that stack into slices ("stages") and puts each slice on its own GPU(s), so a model can be trained across many GPUs.
  2. Data flows through the stages like an assembly line: each stage passes its output to the next, and during learning the corrections flow back the other way.
  3. Each stage is run by an ordinary DeepSpeed engine, and the stages are started and connected by Ray; neither library was modified.
  4. What's new compared with NVIDIA's Megatron: every stage can have a different number of GPUs and a different way of using them. That matters because the last stage (which holds the output layer) does about twice the work of the others.
  5. Every configuration was checked to produce the same numbers as training the unsplit model on one GPU. Those strict checks caught six real bugs, which are now fixed.
  6. From the same pretrained weights and text, rdsp and Megatron produce the same loss curve at 1, 4 and 8 GPUs (within 0.05% per step). With every setting matched, precision included, on the same pinned-H100 machine, rdsp is on par with Megatron or faster. With small microbatches, where Python overhead dominates, it leads by 1.24–1.30×. In GPU-bound training with large microbatches and Megatron's fastest options, it leads by 1.10× at 1 GPU and 1.11× at 4, and ties at 8 (Chapter 13).
  7. The core idea, a second GPU for the busiest stage, didn't pay off on this model. In three fair tests, a plain 5-stage pipeline beat 4 stages with a 2-GPU last stage by 3–9%: two GPUs made that stage only ~1.5× faster. rdsp still beat Megatron's best layouts by 1.18× at the same GPU count.

1The problem

Why split a model across GPUs at all, and why by depth?

Training a language model means showing it text, measuring how wrong its predictions are, and nudging millions of numbers (its weights) to be a little less wrong. Big models don't fit on one GPU, or train too slowly on one. So the work has to be split across GPUs. There are three basic ways to split it:

Split the data

Data parallel: every GPU holds the whole model and trains on different examples; afterwards they average what they learned. Simple, but every GPU must fit the whole model.

Split each layer

Tensor parallel: each big matrix is cut into slices across GPUs. Works for huge layers, but GPUs must talk to each other inside every layer, so it needs very fast links.

Split by depth

Pipeline parallel: GPU 1 holds layers 1–7, GPU 2 layers 8–14, and so on. GPUs only talk at the cut points, once per chunk of data. This is what rdsp does.

Real systems combine all three. rdsp's organizing idea is pipeline parallelism, and inside each stage it can also use data, tensor, sequence or expert parallelism (Chapter 7).

The part that motivated the project: stages don't do equal work

In a language model the last layer (the output head) turns each position into a score for every word in the vocabulary: 151,936 words for Qwen3. That one layer costs about a quarter of the model's compute. So if you cut 28 layers evenly into 4 stages, the last stage does about 2.3× the work of the others. In our early measurements it was 85% busy while a middle stage sat at 29%.

Megatron, the most widely used pipeline system, supports full 3D parallelism (tensor, pipeline and data, plus context and expert), but with one shape for the whole job: every stage gets the same number of GPUs, split the same way. rdsp's reason to exist is to let each stage be shaped for its own workload, for example giving the busy last stage more GPUs.

The ground rules we set ourselves

  • No forks. DeepSpeed and Ray are used only through their public interfaces. Zero lines changed in either, and a check against the pinned DeepSpeed source proves it.
  • A familiar interface. rdsp.initialize(...) looks like deepspeed.initialize(...), and engine.train_batch() performs exactly one optimizer step.
  • The same numbers. A split model must learn exactly like the unsplit model, checked number by number, not just "it runs".
import rdsp
engine, _, _, _ = rdsp.initialize(
    model=hf_model,                       # a normal Hugging Face model
    config=deepspeed_config,              # a normal DeepSpeed config
    pipeline_config=rdsp.PipelineConfig(stages=4, partition=rdsp.UniformTransformerBlocks()),
    loss_fn=my_loss)

for _ in range(steps):
    loss = engine.train_batch()           # one call = one optimizer step

3How a pipeline trains

Forward, backward, and the assembly line

One training step on a single GPU has three parts:

  1. Forward pass. Text goes in at the bottom of the layer stack; each layer transforms it and hands the result up. The intermediate results are called activations. At the top, the model's predictions are compared with the right answers to get the loss (a single "how wrong" number).
  2. Backward pass. Starting from the loss, we go back down the stack computing, for every weight, which direction would reduce the loss. These are the gradients. Each layer needs the activations it saved during the forward pass.
  3. Optimizer step. Every weight moves a little in its gradient's direction.

Split across GPUs

With the stack split into stages, the forward pass becomes a relay: stage 0 computes its layers and sends its activation to stage 1, and so on up to the last stage, which computes the loss. The backward pass runs the relay in reverse: the last stage computes "how the loss changes with respect to its input" and sends that gradient back to the previous stage, which continues the backward pass from there. It's the chain rule of calculus, split across machines.

Why "microbatches"?

If you push the whole batch through stage 0, then stage 1, then stage 2, only one GPU works at a time. The fix is the assembly line: cut the batch into microbatches. While stage 1 works on microbatch 1, stage 0 already starts microbatch 2. Gradients from all microbatches are added up, and the weights update once at the end, so the result equals processing the whole batch at once.

Even so, at the start of a step later stages wait for their first input, and at the end earlier stages wait for their last gradient. That idle time is called the pipeline bubble. More microbatches shrink it. The next chapter lets you see it.

One subtle rule

The record PyTorch keeps of the forward pass (needed for the backward pass) cannot leave the process that created it. So the GPU that ran a microbatch's forward pass must also run its backward pass, and the loss must be computed on the last stage, where the labels are sent. The driver program never touches activations or weights, only the final loss numbers.

4The schedule

1F1B: the order each stage does its work

Each stage needs a fixed order for its forwards (F) and backwards (B). rdsp uses 1F1B ("one forward, one backward"): each stage does a few warm-up forwards, then alternates one forward with one backward, then finishes the remaining backwards. The alternative, GPipe, does all forwards first. The two orders take the same time, but 1F1B frees each microbatch's saved activations much sooner, so stages need far less memory.

5Architecture

The pieces, and what each one is responsible for

rdsp has two halves. The driver is your Python program: it plans and coordinates, but never holds weights. The stages do the work: each stage is a group of Ray actors, one per GPU, each running a normal DeepSpeed engine on its slice of the model.

What each piece does

Your training script

Builds a Hugging Face model and a normal DeepSpeed config, calls rdsp.initialize, then calls train_batch() in a loop. It gets back a loss number per step and nothing else.

Plan compiler

Reads your settings and produces a frozen plan: which layers each stage owns, how many GPUs it has, how those GPUs split the work, how many microbatches per step, and the DeepSpeed config for each stage. Every mistake (e.g. a batch that can't be split evenly) is rejected here, before any GPU is touched. The plan has a fingerprint (hash) that checkpoints record.

Coordinator

Owns the step. It pulls exactly N microbatches, sends each stage one command, collects the loss, runs the "is everyone ready? then everyone update" barrier, counts steps, and runs checkpoint save and load.

Stage workers (Ray actors)

One process per GPU, placed by Ray on a machine with a free GPU (all of a stage's GPUs on one machine). Each runs the stage's op list: receive → forward → send, and receive gradient → backward → send.

DeepSpeed adapter

Wraps a normal DeepSpeed engine for one stage: mixed precision, the optimizer, ZeRO memory saving, and tensor/sequence/expert parallelism inside the stage. rdsp calls only DeepSpeed's public methods.

Stage-to-stage links

Two extra NCCL channels per GPU, one for activations going forward, one for gradients going back. Tensors move GPU-to-GPU without touching the CPU or the driver.

Why is the driver not allowed to hold tensors?

Two reasons. First, activations can't be used for the backward pass anywhere except the process that produced them (Chapter 3), so shipping them to the driver buys nothing. Second, a driver that touches every tensor becomes a bottleneck and a single point of memory pressure. The rule is enforced by tests: nothing the public API returns can contain a Ray reference or a tensor that requires gradients.

7Stages of different shapes

A stage can use several GPUs, in four different ways

Inside a stage, extra GPUs can split the work in any of four ways. Each one is an ordinary DeepSpeed feature, running inside that stage only.

WayWhat each GPU of the stage getsWhen it helpsDeepSpeed feature
Data parallelA different slice of the microbatch's rows (examples)Plenty of rows; the stage's layers fit on one GPUZeRO 0/1/2
Tensor parallelThe same rows; a slice of every weight matrixVery large layers; fast GPU linksAutoTP
Sequence parallelThe same rows; a different stretch of the textVery long sequencesUlysses
Expert parallelA different slice of the rows; some of the "experts"Mixture-of-experts modelsAutoEP (+ "folding" with tensor parallel)

Each stage declares its GPU count and its tensor/sequence/expert degree; the data-parallel degree is whatever is left. At startup, DeepSpeed reports each GPU's position in its stage, and rdsp refuses to run if that doesn't match the plan.

The boundary problem: when neighbours split the data differently

Suppose stage 1 splits each microbatch's rows between 2 GPUs and stage 2 splits them between 4. Stage 1's GPUs each hold half the rows, and stage 2's GPUs each need a quarter. rdsp works out, for every receiving GPU, exactly which pieces of which sending GPUs overlap its slice. It sends only those pieces and stitches them together on arrival. Nothing is ever gathered in one place. The same routine runs in reverse for gradients.

Interactive: who sends what at a boundary

The gradient-scale rule (the subtle part)

DeepSpeed assumes each GPU's loss is the average over its own rows, and so it averages gradients across a stage's data-parallel GPUs. But it adds gradients across sequence-parallel GPUs, because each holds a different stretch of the same rows. When a gradient crosses from a stage with 1 data-parallel GPU into a stage with 2, it must be rescaled so that after DeepSpeed's averaging each weight gets the true gradient. rdsp's rule: the gradient entering stage s is multiplied by (data-parallel GPUs of s) ÷ (data-parallel GPUs of the next stage).

Worked example

Last stage: 1 GPU. The previous stage: 2 data-parallel GPUs. The last stage computes the true gradient for all rows, g. Each of the previous stage's GPUs gets its half of g, runs backward, and gets weight-gradients w₁ and w₂, whose sum is the true weight gradient. DeepSpeed then averages: (w₁+w₂)/2, which is half the truth. Multiplying the incoming gradient by 2/1 = 2 first makes the average exactly right.

We initially applied this rule to sequence-parallel GPUs too, which doubled their updates, because DeepSpeed adds rather than averages over them. A per-weight comparison test caught it (Chapter 14).

8Staying correct

Five rules that keep a split model identical to an unsplit one

1 · Nobody updates alone

After all backwards, the coordinator asks every stage "are you completely done?" Only if all say yes does it tell all of them to run the optimizer, exactly once. Weight updates on different machines can't be undone, so this barrier matters.

2 · Add, don't replace

Gradients from N microbatches must be added up. DeepSpeed decides when to add using an "accumulation boundary"; rdsp marks only the last backward of the step as the boundary. (Without that, ZeRO-1/2 silently kept only the last microbatch.)

3 · A failed step leaves no trace

If a step fails before the update, every stage throws away that attempt's activations, partial gradients and even its random-number draws, so a retry equals a clean step exactly.

4 · Half-updated means locked

If a failure happens during the update, some stages may have updated and some not. The engine then locks ("poisoned") and refuses every call until restored from a checkpoint. Refusing loudly beats silently training a half-updated model.

5 · No per-stage gradient clipping

DeepSpeed clips gradients by default, but per stage, which is a different algorithm from clipping the whole model. rdsp turns it off and rejects an explicit setting until whole-pipeline clipping exists.

How a failure shows up

You always get one of rdsp's own errors: StepFailed (nothing changed, retry is safe) or PipelinePoisoned (restore required). Never a raw Ray or NCCL exception.

The backward handoff trick

DeepSpeed's public backward function only accepts a single number (a loss). A middle stage has no loss, only an incoming gradient g for its output. rdsp hands DeepSpeed the number (output · g).sum(), whose derivative with respect to the output is exactly g. Tested against an unsplit model, gradients came out bit-identical under every ZeRO mode, in bf16, with accumulation.

9Checkpoints & recovery

One consistent snapshot across every GPU

Each stage saves itself using DeepSpeed's own checkpoint function (weights, optimizer, learning-rate schedule). rdsp adds what makes the separate files belong together:

  1. Save. Every GPU of every stage saves; each also saves its random-number state. The driver records how many microbatches the data loader has handed out.
  2. Fingerprint. Each stage computes a fingerprint (SHA-256) of every file it wrote.
  3. Commit. Only when every GPU has reported success does the driver write a small manifest.json listing every file, its fingerprint, the plan's fingerprint and the step number. A folder without a manifest is an unfinished save and is never loaded.
  4. Load. The manifest is checked first: same plan? all files present and unchanged? Then every stage re-checks its own files on its own machine, and only if all pass does any stage load.
  5. Recover. If a GPU worker died, loading tears the whole pipeline down, rebuilds it (preferring the same machines, so their local files are still there), then loads.
Tested property

Train, save, keep training. Then build a brand-new pipeline from different random weights, load, and keep training. Its losses match the original run bit for bit, including the dropout randomness and the position in the data.

11rdsp vs Megatron

Same pipelining idea, different ownership of each stage

Megatron-LM is NVIDIA's training framework and the de-facto standard for large-scale pipeline training. Both systems split the model by depth, use 1F1B, and move tensors between neighbouring GPUs with NCCL. The difference is where the structure lives.

Megatron-LMrdsp
Shape of stages3D parallel (tensor × pipeline × data, plus context and expert), but one TP × DP shape for every stageEach stage its own GPU count and parallelism
Who runs the scheduleEvery GPU process runs the whole schedule itself, inside one torchrun jobEach stage's workers run their own op list; a driver starts each step and runs the update barrier
How workers startA fixed set of processes launched togetherRay places each stage's workers where GPUs are free, and can rebuild them
Model codeMegatron's own model definitions; HF weights must be convertedThe unmodified Hugging Face model, split by layer names
Inside a stageMegatron's own tensor / context / expert parallel layersA stock DeepSpeed engine (ZeRO, AutoTP, Ulysses, AutoEP)
KernelsTransformer Engine fused kernelsHF layers; fused kernels via Liger in our benchmark
Balancing uneven stagesCan move layers between stages (layout string)Can move layers and give a stage more GPUs
FailuresRestart the job from a checkpointClean error and retry; lock and whole-pipeline restore
MaturityProduction-scale, thousands of GPUsResearch prototype; tested on one machine
Trade-off in one sentence

rdsp buys per-stage flexibility with an extra coordination layer (Ray and a driver). Megatron has no such layer, so it wastes less time between GPUs; rdsp's job is to make that layer cheap enough (Chapter 12).

12First design → fix

How profiling changed the design

The first design: the driver sent every operation

Originally the driver sent every single forward and backward to every stage as its own Ray call, and Ray carried the tensors between stages. It was simple, and correct. But at 8 stages it got slower than at 4 (43.5k → 36.8k tokens/s on H100). A profile showed why (these profile runs landed on H200s):

First design, H200, 16 microbatches4 stages8 stages
Step time742 ms831 ms
Each GPU idle37–42%60–66%
Idle expected from the schedule alone16%30%
Real compute per forward/backward call12.8 ms8.4 ms
Ray overhead per call4.7 ms4.9 ms
Ray calls per step~424~944

Doubling the stages halved each call's real work, but the ~5 ms of fixed overhead per call stayed. And because the pipeline runs its slots back to back, the overhead sat on the critical path every time. (Set the overhead slider in Chapter 4 to about 60% to see the same effect.)

The fix: each stage runs its own schedule

Now the driver sends each stage one command per step containing its whole op list, and neighbouring stages exchange tensors directly over two NCCL channels per GPU. At 8 stages, Ray calls per step fall from about 944 to about 16. The computation is unchanged: the new path produces bit-identical numbers to the old one.

Why two channels, one per direction?

NCCL processes the messages on one channel strictly in order. If activations and gradients shared a channel, a stage's "receive gradient" could get stuck behind its own "send activation", and its neighbour's behind theirs, a deadlock. With one direction per channel, messages always flow one way, and the 1F1B order guarantees every receive's matching send eventually happens.

How to read it

  • The apples-to-apples result: with every setting matched, precision included, on the same pinned-H100 machine, rdsp is 1.24× faster at 1 GPU, 1.30× at 4 and 1.29× at 8. Both frameworks learn identically (below).
  • Where the lead comes from: it's already there on one GPU, where no pipelining happens, so it isn't an advantage of rdsp's pipeline design. The profile below shows it's mostly lower Python overhead in this small-microbatch setting, plus a cheaper cross-entropy. The pipeline holds the lead at 4 and 8 GPUs (1.30×, 1.29×) and doesn't lose it.
  • Precision barely matters. Switching Megatron to bf16 summing changed its speed by −3% to +2% at every size. So rdsp's lead isn't a precision artefact.
  • Machines vary; ratios hold. An earlier 4-GPU machine ran both frameworks ~25% faster (Megatron 441 ms, rdsp 321 ms), but the ratio (1.37×) was similar. Absolute speeds and speed-ups across GPU counts therefore aren't reliable; same-machine ratios are.
  • An earlier 1-GPU figure was wrong. Before this run, a cross-machine comparison suggested rdsp led by only ~1.11× at 1 GPU. The same-machine run says 1.24×.

With every setting matched, you might expect equal speed on one GPU. How the weights were moved into Megatron

Megatron fuses the query, key and value projections into one matrix, ordered by attention head group: for each of the 8 key/value groups, the 2 query heads, then the key head, then the value head. The Hugging Face q/k/v matrices were reshaped and interleaved into that order; gate and up projections were stacked into Megatron's first MLP matrix; the norms went into Transformer Engine's fused layer-norm slots. One quirk: Megatron divides the loss by the microbatch count in place, and a detached copy of it for logging shares that memory. So the first run logged values exactly 8× too small, while the gradients were unaffected. We corrected by ×8 and fixed the logging.

The core idea, tested fairly: does the busy stage benefit from a second GPU?

The stage holding the output layer (the "head") does the most work. rdsp can give that one stage 2 GPUs; Megatron can't. We tested it on one pinned-H100 machine with large microbatches, against the best layouts both frameworks can build by moving layers between equal stages.

  • rdsp beats Megatron in every matched layout, by 1.18× at both 4 and 5 GPUs. Every setup trained to the same loss (median per-step difference ≤ 0.13%).
  • The uneven setup lost to simply adding a 5th stage. With 5 GPUs, rdsp's plain 5-stage layout was 7% faster than the 2-GPU head stage.
  • Why: we expected the head to cost about 10 layers' worth of time, based on arithmetic. In practice it's a single large, efficient matrix multiply, while each layer runs many small operations. Timed, the head is closer to 5–6 layers. So a 5th equal stage already spreads the work almost evenly, and the 2-GPU head stage adds overhead with nothing to gain: the two GPUs must sync their gradients, and each microbatch is split between them.

A second chance, with the prediction written down first. That test gave the uneven setup a lopsided layout (8-8-8-4). By the same reasoning, its fair layout is 7-7-7-7: the same slowest-stage work as 5 equal stages, but one fewer stage. We predicted it would win by ~1.14× with 4 microbatches, where each extra stage adds a lot of idle time, and by ~1.05× with 16. Same machine, back to back:

rdsp, one pinned-H100 machine5 equal stages: 7 · 7 · 7 · 6 · 1+H, 1 GPU eachUneven: 7 · 7 · 7 · 7+H, last stage on 2 GPUsUneven vs equal

  • The prediction was wrong both times. The 2-GPU stage was itself the bottleneck: ~26–28 ms per microbatch, where the other stages took ~23 ms. Two GPUs made that stage only about 1.5–1.6× faster, not 2×. Splitting each microbatch in half leaves each GPU too little work to run efficiently, and the two GPUs also sync gradients and split and reassemble the data between stages.
  • Verdict for Qwen3-0.6B: adding a stage always beat giving one stage a second GPU. The idea can only pay off when a stage's work is large enough to split efficiently across GPUs, and can't be spread by moving layers. Examples: a much bigger model, a huge vocabulary, a vision encoder, or a stage that runs out of memory. Testing that would need a larger model than this project used.

Earlier, a similar table said extra GPUs made rdsp slower. That table compared runs on different chip types (H100 vs H200) using the first design, and is superseded by this one.

Making the test strict enough to trust

  • SGD, not Adam. Adam ignores a gradient that is uniformly too big or too small, so an early Adam-based test passed a deliberately broken build. Plain SGD exposes any scale error.
  • A sensitivity check. The test refuses to run unless each step moves the loss by at least 20× the tolerance, so an error can't hide inside it.
  • Per-weight comparison. For tensor/sequence/expert parallel, every weight's one-step change is compared with the unsplit model's.
  • Failure drills. Each configuration also saves and restores, and has a GPU worker killed mid-training and recovered.

The six bugs these tests caught

ZeRO-1/2 kept only the last microbatch

Gradients were replaced instead of added. Fixed by marking only the last backward as the accumulation boundary.

Qwen3 head norms under tensor parallel

Each GPU saw only its own heads' part of the norm gradients; GPUs drifted apart. Fixed by summing them.

Sequence-parallel updates doubled

The gradient-scale rule treated sequence shards like data-parallel GPUs. Fixed (Chapter 7).

Folded experts sent a partial gradient

Each GPU held a different partial gradient below expert layers. Fixed by averaging at the expert layer's input.

Failed steps left traces

Gradients and random draws from an abandoned step leaked into the retry. Now discarded.

Silent per-stage clipping

DeepSpeed's default clipping ran per stage. Now off; explicit clipping is rejected.

Totals: 290 CPU tests and 32 GPU tests (8×L4, real DeepSpeed, NCCL) pass on the final design.

15Limitations

What these results do not show

  • One run per cell, and machines vary. The same configuration varied by up to ~20% between machines, so only same-machine comparisons are reliable.
  • Earlier results mixed chips. Modal ran some "H100" jobs on H200s, and the first headline compared rdsp on H200 with Megatron on H100. Those comparisons are withdrawn; the harness now refuses non-H100 machines.
  • rdsp's speed lead depends on the regime. It's 1.24–1.30× with small microbatches, where Python overhead dominates. In GPU-bound runs it's 1.10× at 1 GPU and 1.11× at 4, a tie at 8. Megatron's pure GPU work is slightly less. Larger models are untested.
  • One small model, one machine. Everything was measured on a 0.6B model; larger models are untested.
  • Multi-machine is untested. The 32-GPU, 4-machine topology never ran (the Modal account allows 10 GPUs at once, and multi-machine Modal needs 8 GPUs per machine). The multi-machine code paths are exercised on one machine only.
  • Scaling across GPU counts isn't measured reliably. Each GPU count ran on a different machine, and machines differ by up to ~25%. Beyond 8 stages is unmeasured.
  • Heterogeneous stages didn't pay off on this model. A second GPU for the head stage lost to a plain 5-stage pipeline by 3–9% in three fair tests (4 and 16 microbatches, two layouts). Splitting a stage's small microbatches across two GPUs gains only ~1.5×.
  • No whole-pipeline gradient clipping.
  • DeepSpeed constraints: sequence parallel can't be on the last stage; tensor and sequence parallel can't share a stage.
  • Model support: plain layer stacks and Llama/Qwen-style HF models split automatically; other architectures need their own stage type.
  • Checkpoints on local disks survive a crashed worker, not a lost machine.

Future work

  1. Heterogeneous stages on a larger model, where one stage's work is big enough to split efficiently across GPUs. This is the one setting where the project's core idea could still pay off.
  2. The 32-GPU, 4-machine topology, with a higher GPU limit or on AWS.
  3. Repeats of the same-machine cells, to put error bars on the 1.1–1.2× speed leads.

16FAQ

Questions people ask

Why not just use DeepSpeed's own pipeline engine?

DeepSpeed's PipelineModule also requires every stage to share one shape, and it runs as one fixed job like Megatron. rdsp's point is per-stage shapes; it reuses DeepSpeed for everything inside a stage.

Why Ray?

Ray starts a worker process on any machine with a free GPU, lets the driver call methods on it, reports when it dies, and lets us rebuild it. That is what makes "stage 3 gets 4 GPUs, stage 1 gets 2" and whole-pipeline recovery straightforward. After the redesign, Ray is used for control (one call per stage per step), not for moving tensors.

Does the driver become a bottleneck?

Not anymore. In the stage-local design it sends one command per stage per step and receives one loss list, about 16 Ray calls per step at 8 stages. Its submission work was already off the critical path in the profile.

What does "bit-identical" mean here?

For the dispatch redesign, the old and new paths were run from the same weights and data and produced exactly the same floating-point losses. For split vs unsplit models, results match within tiny rounding differences (1 part in 10,000 or better in fp32), because adding numbers in a different order rounds slightly differently.

What is RDT, and is it still used?

Ray Direct Transport lets Ray move GPU tensors between actors without a CPU copy. It sped up the first design by 6–18%. The stage-local design makes it unnecessary: tensors go over rdsp's own NCCL channels. RDT was removed together with the older driver-dispatch mode.

How do I choose stage shapes?

Today: give each stage enough GPUs to fit its layers, use data parallel when there are enough rows to split, tensor parallel only within one machine, and consider moving layers off the last stage. The measurements so far don't yet show heterogeneous shapes beating uniform ones at small scale; that is the open experiment.
