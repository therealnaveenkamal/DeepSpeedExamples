Qwen3.5-35B-A3B vision-language training · two nodes of 8× H100 · EFA network · Oct 18, 2026

rdsp on Two Nodes

On 16 GPUs across two nodes, rdsp trains the sparse Qwen3.5-35B-A3B at 1,273 real tokens per second per GPU: 1.86× TorchTitan's best (686) and 2.3× Megatron-Bridge's own recipe (544). MegatronMIMO cannot train this model. rdsp wins by giving the vision encoder GPUs of its own, which only pays off when the language model is sparse.

Four terms used below

Sparse model
A mixture-of-experts model: each layer holds 256 small "expert" blocks and each token goes through 8 of them. The 35B-A3B has 35 billion parameters but uses about 3 billion per token. The 27B is dense: every token uses all of it.
Pipeline stage
A slice of the model's layers on its own GPUs. Stages hand their activations to the next stage.
Vision stage
A first stage that holds only the vision encoder (the part that reads images), with its own number of GPUs. Only rdsp can give one stage more GPUs than the others.
Real tokens
Tokens that are not padding: 129,997 per step on average, the same 128 rows of 2,048 for every system.

Why: in a sparse model the vision encoder is the bottleneck

rdsp times every stage before it cuts the model. With 5 layers on each of 8 stages, the stage that also holds the vision encoder took 11.9 s per step and the next stage 3.4 s. 79% of real tokens are image tokens, and the 35B's vision encoder is as large as a dense model's, while each language token touches only about 3B parameters. Moving layers off that stage helps only until it holds the encoder alone; after that, step time follows the number of GPUs the encoder gets:

Same layouts, same nodes, same rows. The dense 27B's language layers do about nine times the work per token. Taking 4 GPUs for vision leaves its language model 12 GPUs, at 8.3–9.6 s per stage, and that sets the pace. On the sparse model the language stages stay at 3.7–4.9 s. A vision stage of its own pays off where the language model is light per token and the vision encoder is not.

Where TorchTitan's step goes

An Nsight Systems profile of TorchTitan's 8 GPUs on the first node, 36 seconds of steady training: each GPU ran communication kernels for 29–30 s (about 83%) and matrix multiplies for 2.2 s (6%). Fully sharded training gathers every layer's full weights onto every GPU for every microbatch: all 35B parameters, including all 256 experts, while each token uses 8 experts. rdsp's pipeline keeps each stage's weights on its own GPUs and sends only activations between stages. TorchTitan's own log reports 2.7% of the GPUs' peak math rate.

How the runs were set up

  • Two AWS p5.48xlarge (8× H100 80 GB each), one placement group, EFA between the nodes: all-reduce of 1 GiB over all 16 GPUs at 435 GB/s.
  • Equal work: the same 128 rows of 2,048 tokens per step (Megatron-Bridge's rows, exported once), loss averaged over every token of the step, AdamW at a constant learning rate of 1e-5, bf16 weights and gradients, 32-bit master weights stored in 2 bytes where the system supports it, 50 steps, median of steps 6–50. No router load-balancing loss on any system; the extra prediction layer off.
  • Same work checked: rdsp and TorchTitan losses agree to within 0.2% over the first steps (0.732, 0.404, 0.176). Megatron-Bridge reports its loss only to TensorBoard, so it is not compared.
  • Recompute only when a run ran out of memory without it, the same rule for every system.
  • NeMo 26.08 container for Megatron-Bridge and MIMO (Megatron-Bridge 0.6.0), TorchTitan at 3c36a77, DeepSpeed at 53a2ac4, transformers 5.17.0.

Limits

  • One run per setting. Step times within a run vary by about 2%.
  • rdsp picks the vision stage's GPU count from measured time only, not memory. For the dense 27B it chose the vision stage, which needed full recompute and lost to 8 stages.
  • A slower network than EFA (plain TCP) was not tested for rdsp or TorchTitan.
  • Megatron-Bridge's best number comes from splitting the experts across GPUs, which no other row does. A first run of it, with our earlier docker settings that dropped a CUDA library from the container's path, took 15.72 s; the 14.94 s above is the rerun with those settings fixed.
